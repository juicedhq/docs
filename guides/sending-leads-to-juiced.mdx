Once you've [set up a source](/guides/setting-up-a-source-and-its-attributes), you're ready to start sending leads. Submissions go to a single REST endpoint, authenticated with the source's credentials, with the payload shaped by the source's [fields](/features/lead-categories#field-types) and required-for-post settings.

This guide walks you through making your first submission end-to-end, from pulling credentials and reading the field reference to posting a lead and confirming it was accepted.

## Prerequisites

- A source configured for the lead category you want to ingest into. If you don't have one yet, see [Setting Up a Source and Its Attributes](/guides/setting-up-a-source-and-its-attributes).
- Something to make HTTP requests with, like `curl`, Postman, your application code, or whatever your integrator uses.

## 1. Open the source's API specification

Open **Sources** under **Ingest** in the sidebar and click the source you're integrating. On the source's **Overview**, open the **More actions** (⋯) menu in the header and choose **View API Spec**.

  <img className="hidden dark:block" src="/images/tenant/ingest/source-detail-dark.webp" alt="Source overview with the Edit button and the More actions menu in the header" />

A new tab opens with a shareable page titled "API Specification for [Source Name]". This page contains everything an integrator needs, including credentials, the endpoints, example requests and responses, and the full field reference.

<Warning>
The API spec link is a signed URL that expires in 7 days. After that, the link stops working. If you need to share it again, come back to the source and choose **View API Spec** to generate a fresh link.
</Warning>

## 2. Grab authentication credentials

The first section of the API spec is **Authentication**. Juiced supports two auth methods, so pick whichever fits your integration.

| Method | How it works |
|--------|-------------|
| **HTTP Basic Auth** | Uses the source's **API Key** (username) and **API Secret** (password). Both are shown in plain text on the spec page. |
| **Bearer Token** | Authenticate with a token in the `Authorization: Bearer <your_token>` header. Generate one on the source's **Authentication** tab inside Juiced by clicking **New bearer token**. The token is shown once, so copy it right away. |

<Tip>
On the spec page, expand **Manually constructing the authorization header** for the exact base64-encoded value to use with Basic Auth.
</Tip>

## 3. Review the field reference

Scroll down to **Field Reference**. The table lists every field this source accepts, what type it is, whether it's required for pings, required for posts, and a realistic example value.

The fields marked **Required for post** must be present in every lead submission or the API returns a `422` with a list of validation errors. Fields marked **Required for ping** must also be present when using [ping-post](/features/ping-post).

Fields typed as **List of Values** show the allowed values next to the example. Any submitted value outside that list will fail validation.

<Note>
The Field Reference is the source of truth for what this source accepts. It automatically reflects both lead category fields and any source-level fields you've added (except fields hidden from the API spec), so integrators don't need to ask "what fields do I send?" because they can see it here.
</Note>

## 4. Submit a lead

Send a `POST` to the v1 leads endpoint, `https://usejuiced.com/api/v1/leads`. The spec page includes a copy-paste-ready **Example cURL Request** block with your credentials already baked in. If its URL ends in `/api/leads`, change it to `/api/v1/leads`. Here's the general shape.

```bash
curl -X POST \
  -H "Authorization: Basic <base64(api_key:api_secret)>" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "transaction_id": "order-10482",
    "first_name": "Katy",
    "last_name": "Berry",
    "email": "katy.berry@example.com",
    "phone": "555-123-4567",
    "address_1": "742 Orchard Lane",
    "city": "Paradise Bay",
    "state": "FL",
    "zip": "33139"
  }' \
  https://usejuiced.com/api/v1/leads
```

The `transaction_id` is optional but worth sending. It's your own ID for the lead, so if a request times out you can safely send it again without creating a second lead. See [Safe retries](/api-reference/introduction#safe-retries-with-transaction-id) for the details.

A submission that passes validation returns `201 Created` with a body like this one.

```json
{
  "data": {
    "id": "lead_01jbx8m2d4f6g8h0j2k4m6n8pq",
    "status": "accepted",
    "price": 45
  },
  "version": "v1"
}
```

`data.status` is one of three values, decided by the source's [status responses](/features/sources#status-responses) mapping.

| Status | What it means (by default) |
|--------|--------------|
| `accepted` | The lead was assigned, posted to a partner, placed on the [marketplace](/features/marketplace), or parked in the [Club](/features/club). `price` is what the source earns for it. |
| `rejected` | The lead was valid but ended up Unassigned, Audit, or Uncategorized. `price` is `0`. |
| `duplicate` | The lead matched a [duplicate check](/features/duplicate-detection). No charge, no distribution, and `price` is `0`. |

If you've changed the source's status response mapping, the statuses behind each value change with it. Your own lead's actual status is always visible on its page in Juiced.

<Warning>
Validation failures return `422` with the error code `validation_failed` and an `errors` object keyed by field. Fix the payload and re-submit. The original submission is recorded as rejected and won't be retried automatically.
</Warning>

<Note>
Already sending leads to `/api/leads`? That's the legacy API. It still works, but it's deprecated, so plan a move to v1. Its success status is `success` rather than `accepted`, and its fields sit at the top level of the response rather than under `data`. See [Moving from legacy to v1](/api-reference/introduction#moving-from-legacy-to-v1).
</Note>

## 5. Verify the submission landed

Back in Juiced, open **Incoming logs** under **Entries** in the sidebar. Every submission gets an incoming log, newest first, showing the source, the post's outcome, the lead it created, and who bought it.

Click the log, then the **Post** link under **Records**, to open the post inspector.

<Frame>
  <img className="block dark:hidden" src="/images/tenant/logs/post-inspector-light.webp" alt="Post inspector with the request payload, Juiced's response, and Details and Records in the sidebar" />
  <img className="hidden dark:block" src="/images/tenant/logs/post-inspector-dark.webp" alt="Post inspector with the request payload, Juiced's response, and Details and Records in the sidebar" />
</Frame>

- **Request** shows the **Payload** exactly as received, plus **Validation errors** when the post was rejected.
- **Response** shows what Juiced sent back.
- **Details** shows the post's status (**Accepted** or **Rejected**) and response code (`201` or `422`).
- **Records** links to the lead the post created, if any.

This is the first place to look when an integrator says "I sent a lead but didn't see it." See [Logs](/features/logs) for everything else the logs can tell you.

<Tip>
Test traffic is hidden by default. If the source is in test mode, set the **Test mode** filter on Incoming logs to **Test only** to find those requests.
</Tip>

## Testing without real data

If your source is in **test mode** (switched on from the source's edit form), you can submit leads using test zip codes without touching production data.

| Zip | Response `data.status` (default mapping) | Lead status |
|-----|----------|-------------|
| `00001` | `accepted` | Assigned |
| `00002` | `duplicate` | Duplicate |
| `00003` | `rejected` | Audit |
| `00004` | `rejected` | Unassigned |
| `00005` | `accepted` | Marketplace |
| Any other zip | `rejected` | Marked as test data and moved to Audit |

<Tip>
Test mode is the right tool for integration development and vendor sandboxing. Turn it off before going live, because leads posted while test mode is on won't be distributed to real customers.
</Tip>

## What happens next

Once a lead is accepted, a few things follow.

- **Matching** runs immediately. Juiced classifies the lead into a [lead type](/features/lead-types) and runs it through your [distribution stages](/features/distribution).
- **The response** tells you the outcome before the API call returns.
- **Delivery** follows if the lead was assigned, so the customer sees it in their portal and any configured [webhooks](/features/webhooks) fire.
- The **Leads page** lists every accepted lead under **Entries** → **Leads** with its full history.

If you're expecting higher volume or want to check price and availability before committing to a full submission, see [ping-post](/features/ping-post) for the two-phase submission flow.
